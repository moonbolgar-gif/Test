# DECISIONS — журнал технических решений (ADR)

Формат: одно решение = одна запись. Статус: `принято` / `отменено` / `требует подтверждения`.
Правило из [SPEC.md §20](./SPEC.md): каждое техническое решение фиксируется здесь с обоснованием.

---

## ADR-001 — Стек: React Native, а не Flutter

**Статус:** принято
**Контекст:** SPEC §3.1 допускает Flutter как альтернативу, решение оставлено за техлидом в Фазе 0.
**Решение:** React Native.
**Обоснование:** репозиторий уже проинициализирован на RN; выбор Flutter означал бы старт с нуля.
SPEC прямо запрещает смешивать стеки, поэтому фиксируем один.
**Последствия:** экосистема будильников в RN беднее, чем во Flutter (`android_alarm_manager_plus`,
`flutter_local_notifications`). Нативные модули `RiseAlarmModule` и `RiseVideoModule` пишем сами —
это заложено в SPEC §3.1 и является основным содержанием Фазы 0.
**Требует подтверждения техлида** — если у команды сильнее компетенция во Flutter, это решение надо
пересмотреть **до** Фазы 0, а не после.

## ADR-002 — Expo prebuild (CNG) вместо bare-workflow и вместо Expo Go

**Статус:** принято
**Контекст:** SPEC §3.1 требует «bare workflow, без Expo Go», но тут же разрешает Expo Modules через
`expo-modules-core` + prebuild. Это два разных ограничения, которые легко спутать.
**Решение:** Expo SDK с `expo prebuild` (Continuous Native Generation) + `expo-dev-client`.
Expo Go не используется — он не умеет загружать кастомные нативные модули.
**Обоснование:** ограничение SPEC направлено против Expo Go (в нём невозможен `RiseAlarmModule`),
а не против Expo как такового. Prebuild даёт полный доступ к `ios/` и `android/`, то есть все
возможности bare-workflow, но сохраняет управляемые обновления SDK. Это буквально тот вариант,
который SPEC разрешает явно.
**Последствия:**
- разработка ведётся только на dev-client-сборках, `expo start --dev-client`;
- нативные папки `ios/` и `android/` генерируются и **не коммитятся** (см. `.gitignore`);
- как только в `ios/`/`android/` появятся ручные правки, которые нельзя выразить config-плагином,
  придётся либо писать config-плагин, либо перейти на настоящий bare (закоммитить нативные папки).
  Ожидаемо это произойдёт при `RiseAlarmModule` — решение принять в Фазе 0.

## ADR-003 — Версии: Expo SDK 54 / RN 0.81 / React 19.1

**Статус:** принято (пересмотрено)
**Контекст:** SPEC §3.1 требует «RN 0.76+ с включённой New Architecture». Изначально был взят
SDK 57 как самый свежий.
**Решение:** понижено до Expo SDK 54 (RN 0.81.5, React 19.1). New Architecture включена явно
(`newArchEnabled: true` в `app.json`).

**Почему пересмотрено:** Expo Go на устройстве владельца продукта поддерживает SDK 54 — App Store
отдаёт последнюю версию, совместимую с установленной iOS, и обновиться там некуда. Проект на
SDK 57 в таком Expo Go просто не открывается («Project is incompatible with this version of
Expo Go»). Пока идёт демо-фаза (ADR-013), возможность открыть приложение по QR-коду важнее
свежести SDK.

**Обоснование, почему это не нарушает SPEC:** §3.1 задаёт нижнюю границу RN 0.76+. RN 0.81.5 её
удовлетворяет с запасом. Требование New Architecture тоже выполнено — в SDK 54 она включена
по умолчанию, флаг проставлен явно, чтобы требование читалось в конфиге.

**Когда поднимать обратно:** после начала Фазы 0. Как только появится `RiseAlarmModule`, Expo Go
перестаёт использоваться в принципе (ADR-013), демо будет открываться через dev-client, и
привязка к версии Expo Go исчезнет. Тогда SDK поднимается до актуального.
**Последствия:**
- Версии всех нативных пакетов берутся из `bundledNativeModules.json` пакета `expo` нужного
  SDK, а не «свежие с npm»: расхождение с этим списком ломает Expo Go.
- Часть библиотек из SPEC надо проверить на совместимость с New Arch до Фазы 1 — в первую очередь
  `react-native-vision-camera` v4 (§4.3), `ffmpeg-kit-react-native` (§4.3, проект архивирован
  апстримом — нужен форк или нативный композитинг) и `react-native-sensors` (§6.11 C).
  Занесено в Фазу 0 как отдельная проверка.

## ADR-004 — Web-таргет удалён

**Статус:** принято
**Контекст:** при первичной настройке проекта в репозиторий были добавлены `react-dom` и
`react-native-web`, потому что шаблон Expo объявляет web в `app.json` и в скриптах.
**Решение:** web-зависимости и web-таргет удалены; `platforms` ограничен `["ios", "android"]`.
**Обоснование:** SPEC §2.2 прямо относит web-версию к тому, что **не входит в MVP**. Ядро продукта —
будильник (§4.1) и запись видео (§4.3) — в браузере нереализуемо в принципе.
**Последствия:** `npm run web` больше нет. Если web понадобится как лендинг под инвайт-ссылки
(§7.7, `rise.app/j/{code}`) — это отдельный проект, а не таргет мобильного приложения.

## ADR-005 — Монорепозиторий на npm workspaces

**Статус:** принято
**Контекст:** SPEC §3.2 задаёт структуру с `apps/mobile`, `packages/shared`, `supabase/`.
**Решение:** npm workspaces (`apps/*`, `packages/*`), единый lock-файл в корне.
**Обоснование:** структура задана SPEC; npm workspaces — минимальный инструмент, который её
поддерживает, без добавления Nx/Turborepo. Соответствует правилу «выбирай самое простое решение».
**Последствия:** Metro должен резолвить символические ссылки из корневого `node_modules`.
Проверено: импорт `@rise/shared` из `apps/mobile` бандлится без дополнительной настройки
`metro.config.js` (Expo SDK 54). При добавлении второго пакета в `packages/*` проверить повторно.

## ADR-006 — `packages/shared` содержит только типы, без значений денежных долей

**Статус:** принято
**Контекст:** SPEC §8.2 требует хранить доли распределения (`settings.stake_split`) на сервере и
**не хардкодить в клиенте**. SPEC §3.3 — вся денежная логика только на сервере.
**Решение:** в `packages/shared` лежат типы доменных сущностей и только те константы, которые
являются правилами продукта, а не денежной политикой: окно испытания (5 мин), курс деревьев,
множитель RISE+.
**Обоснование:** доли 50/30/20 и сервисный сбор $0.30 — предмет изменения без релиза приложения;
попадание их в бандл клиента означает рассинхрон при первом же изменении конфига.
**Последствия:** экран выбора ставки (§6.6) обязан получать разбивку с сервера и не считать её сам.
Это влияет на дизайн API — нужен эндпоинт, отдающий текущий `stake_split`, до реализации Фазы 5.

## ADR-007 — Фаза 0 не может быть закрыта в текущем окружении

**Статус:** требует подтверждения
**Контекст:** SPEC §17 запрещает начинать Фазу 1, пока не закрыта Фаза 0, а DoD Фазы 0 (§4.1) —
20/20 срабатываний будильника на пяти физических устройствах (2 iPhone + 3 Android, обязательно
Xiaomi/Huawei) при закрытом приложении и включённом энергосбережении.
**Решение:** UI и Фаза 1 не начинаются. В репозитории — только каркас, документы и контракт типов.
**Обоснование:** физических устройств нет; ни симулятор, ни CI не воспроизводят агрессивный киллинг
фоновых процессов MIUI/EMUI, ради которого этот DoD и написан. Заявить Фазу 0 закрытой по
результатам симулятора — значит обойти главную проверку продукта.
**Последствия:** ближайшие шаги, не требующие устройств, перечислены в [BACKLOG.md](./BACKLOG.md),
раздел «Готово к работе». Спайк 2b (заявка в Apple на Critical Alerts entitlement) — **человеческое
действие, не кодовое**, и по SPEC §17 подаётся в первую неделю: рассмотрение занимает недели и
является критическим путём.

## ADR-008 — Финансовые записи переживают удаление пользовательских данных

**Статус:** принято
**Контекст:** SQL в SPEC §9 задаёт `alarm_runs.alarm_id ... on delete cascade` и
`stakes.alarm_run_id ... on delete cascade`, при этом `ledger_entries` ссылается на `stakes`.
Схема в таком виде внутренне противоречива, и это обнаружилось на первом же тесте:
- удаление будильника каскадом сносит срабатывания и ставки, упираясь в `ledger_entries`;
- удаление аккаунта — обязательное по §14.4 требование сторов — ломается по той же цепочке;
- если снять ограничение и разрешить каскад до конца, действие пользователя начнёт уничтожать
  бухгалтерские записи.
**Решение:** ссылки на пользовательские сущности из финансовых таблиц обнуляемые
(`on delete set null`), а не каскадные: `alarm_runs.alarm_id`, `stakes.alarm_run_id`,
`stakes.user_id`.
**Обоснование:** удаление аккаунта обязано удалять персональные данные, но не историю платежей —
это разные вещи и по смыслу, и юридически. Обнуление ссылки обезличивает ставку, сохраняя сумму
и распределение. RLS при этом перестаёт показывать её кому-либо: политика сравнивает `user_id`
с `auth.uid()`, а `null` не совпадёт ни с кем.
**Последствия:** `alarm_runs` и `stakes` должны быть самодостаточны без родителя — поэтому в них
сохранены денормализованные `mode`, `stake_cents`, `challenge_type`, как и было в §9. Проверено
тестом «ставка пережила удаление аккаунта» в `supabase/tests/rls_test.sql`.

## ADR-009 — Таблица `app_settings` и запрет долей в клиенте

**Статус:** принято
**Контекст:** SPEC §8.2 ссылается на `settings.stake_split`, §8.3 — на размер сервисного сбора,
§8.5 — на `feature_flags.money_modes`, но ни одной из этих таблиц в схеме §9 нет.
**Решение:** добавлена таблица `app_settings (key, value jsonb)` с триггером, проверяющим, что
доли распределения дают ровно 100%. RLS отдаёт клиенту только ключи `stake_split` и `service_fee`;
`feature_flags` не виден.
**Обоснование:** без серверного хранения доли неизбежно окажутся в клиентском бандле и
разъедутся с сервером при первом же изменении. Триггер на сумму 100% закрывает класс ошибок,
при которых распределение теряет или создаёт деньги ещё до арифметики.
**Последствия:** аварийный выключатель §8.5 работает без перевыпуска приложения — Edge Function
проверяет флаг перед выдачей SetupIntent. Экран §6.6 обязан получать разбивку с сервера.

## ADR-010 — Денежные модули на чистом TypeScript, тесты в Node

**Статус:** принято
**Контекст:** SPEC §20.3 требует писать тесты на денежную логику до реализации. Edge Functions
исполняются в Deno, но Deno в окружении разработки может отсутствовать.
**Решение:** модули в `supabase/functions/_shared/` написаны без Deno-специфичных API (только
Web Crypto и стандартный JS), тесты запускаются встроенным раннером Node с
`--experimental-strip-types`.
**Обоснование:** один и тот же файл исполняется в проде под Deno и в тестах под Node, без
транспиляции и без второго набора зависимостей. Проверка подписи вебхука вынесена в отдельный
модуль именно ради тестируемости: это единственный неаутентифицированный вход в денежный контур.
**Последствия:** в `_shared/` нельзя использовать `Deno.*` — всё, что требует рантайма, живёт
в `index.ts` конкретной функции. Распределение долей проверяется на каждой сумме диапазона
§14.1 поцентово, а не на нескольких примерах: ошибки округления проявляются именно на
некруглых суммах.

## ADR-011 — Ограничение §15 на удаление денежного будильника живёт в RLS

**Статус:** принято
**Контекст:** SPEC §15 требует блокировать изменение и удаление денежного будильника за 30 минут
до срабатывания, иначе пользователь просто удалит будильник, чтобы не платить. SPEC §10 помещает
это правило в описание эндпоинтов.
**Решение:** правило реализовано политиками RLS на `alarms`, а не только в API.
**Обоснование:** Supabase выставляет таблицы через PostgREST, поэтому клиент может обратиться к
`alarms` напрямую, минуя Edge Function. Проверка, живущая только в обработчике эндпоинта,
обходится одним HTTP-запросом.
**Последствия:** правило выражено в SQL и проверяется тестом на трёх случаях: денежный будильник
за 10 минут (заблокирован), бесплатный за 10 минут (удаляется), денежный за 5 часов (удаляется).

## ADR-012 — Демо-режим: UI на моках при незакрытой Фазе 0

**Статус:** принято (решение владельца продукта)
**Контекст:** SPEC §17 запрещает начинать Фазу 1 до закрытия Фазы 0, а её DoD требует физических
устройств (ADR-007). Владелец продукта решил собрать демонстрационную версию на имитации данных,
отложив реальные интеграции.
**Решение:** экраны §6 собраны поверх состояния в памяти. Реальных будильника, платежей, записи
видео и бэкенда нет.
**Обоснование:** демо решает другую задачу, нежели релиз, — показать продукт и проверить UX. Риск
§17 в том, что UI строится поверх непроверенного ядра; он принят сознательно и ограничен тем, что
демо не выдаёт себя за рабочее приложение.
**Последствия:**
- Экран сработки и кнопка «Промотать до утра» **явно подписаны как симуляция**. §1.3 ставит
  надёжность будильника выше всего: демо, которое выглядит как работающий будильник, но не звонит,
  хуже отсутствия демо.
- Инварианты, которые демо соблюдает несмотря на моки: деньги в центах, доли распределения
  приходят «с сервера» (`src/lib/demoServer.ts`), окно испытания отсчитывает не компонент,
  запрещённая лексика §14.2 не используется, покупка RISE+ не совершается (§8.4).
- Заменяется один модуль: `src/lib/demoServer.ts` → реальный API-клиент. Экраны не меняются.

## ADR-013 — Демо остаётся совместимым с Expo Go

**Статус:** принято
**Контекст:** ADR-002 отказался от Expo Go, потому что в нём невозможен `RiseAlarmModule`. Но
в демо кастомных нативных модулей нет.
**Решение:** для демо взяты только библиотеки, работающие в Expo Go: `expo-sensors` вместо прямой
работы с датчиками, заглушка вместо `react-native-vision-camera`, никакого `ffmpeg-kit`.
**Обоснование:** демо, которое открывается сканированием QR-кода на любом телефоне, показывают
на порядок чаще, чем то, ради которого надо собирать dev-client. Пока нативного кода нет,
платить за него неудобством не за что.
**Последствия:** ограничение действует ровно до начала Фазы 0. Как только появится
`RiseAlarmModule`, Expo Go перестаёт работать и разработка уходит на dev-client. Запись видео
(§4.3) в демо отсутствует именно из-за этого решения: `vision-camera` в Expo Go не работает.

`expo-dev-client` **удалён из зависимостей до Фазы 0**: пока он установлен, `expo start` по
умолчанию уходит в режим dev-client, и запуск демо в Expo Go требует лишних действий. Вернуть
одной командой `npx expo install expo-dev-client` вместе с плагином в `app.json`, когда появится
нативный код.

**Известная ловушка:** каталог `src/app` из структуры §3.2 совпадает с конвенцией Expo Router,
и CLI пишет в лог «Using src/app as the root directory for Expo Router». Сейчас это безвредно —
Expo Router не установлен, точка входа `index.ts` → `App.tsx`. Но если кто-то добавит
`expo-router`, содержимое `src/app` будет истолковано как файловые маршруты. Каталог оставлен
с именем из §3.2; при добавлении Expo Router его придётся переименовать.
