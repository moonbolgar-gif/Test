# DECISIONS — журнал технических решений (ADR)

Формат: одно решение = одна запись. Статус: `принято` / `отменено` / `требует подтверждения`.
Правило из [SPEC.md §20](./SPEC.md): каждое техническое решение фиксируется здесь с обоснованием.

---

## ADR-001 — Стек: React Native, а не Flutter

**Статус:** принято
**Контекст:** SPEC §3.1 допускает Flutter как альтернативу, решение оставлено за техлидом в Фазе 0.
**Решение:** React Native.
**Обоснование:** репозиторий уже проинициализирован на RN; выбор Flutter означал бы старт с нуля.
SPEC прямо запрещает смешивать стеки, поэтому фиксируем один.
**Последствия:** экосистема будильников в RN беднее, чем во Flutter (`android_alarm_manager_plus`,
`flutter_local_notifications`). Нативные модули `RiseAlarmModule` и `RiseVideoModule` пишем сами —
это заложено в SPEC §3.1 и является основным содержанием Фазы 0.
**Требует подтверждения техлида** — если у команды сильнее компетенция во Flutter, это решение надо
пересмотреть **до** Фазы 0, а не после.

## ADR-002 — Expo prebuild (CNG) вместо bare-workflow и вместо Expo Go

**Статус:** принято
**Контекст:** SPEC §3.1 требует «bare workflow, без Expo Go», но тут же разрешает Expo Modules через
`expo-modules-core` + prebuild. Это два разных ограничения, которые легко спутать.
**Решение:** Expo SDK с `expo prebuild` (Continuous Native Generation) + `expo-dev-client`.
Expo Go не используется — он не умеет загружать кастомные нативные модули.
**Обоснование:** ограничение SPEC направлено против Expo Go (в нём невозможен `RiseAlarmModule`),
а не против Expo как такового. Prebuild даёт полный доступ к `ios/` и `android/`, то есть все
возможности bare-workflow, но сохраняет управляемые обновления SDK. Это буквально тот вариант,
который SPEC разрешает явно.
**Последствия:**
- разработка ведётся только на dev-client-сборках, `expo start --dev-client`;
- нативные папки `ios/` и `android/` генерируются и **не коммитятся** (см. `.gitignore`);
- как только в `ios/`/`android/` появятся ручные правки, которые нельзя выразить config-плагином,
  придётся либо писать config-плагин, либо перейти на настоящий bare (закоммитить нативные папки).
  Ожидаемо это произойдёт при `RiseAlarmModule` — решение принять в Фазе 0.

## ADR-003 — Версии: Expo SDK 57 / RN 0.86 / React 19.2

**Статус:** принято
**Контекст:** SPEC §3.1 требует «RN 0.76+ с включённой New Architecture».
**Решение:** RN 0.86 (Expo SDK 57), New Architecture включена явно (`newArchEnabled: true` в `app.json`).
**Обоснование:** требование SPEC — нижняя граница, берём актуальную версию. В SDK 57 New Arch включена
по умолчанию, но флаг проставлен явно, чтобы требование было видно в конфиге, а не подразумевалось.
**Последствия:** часть библиотек из SPEC надо проверить на совместимость с New Arch до Фазы 1 —
в первую очередь `react-native-vision-camera` v4 (§4.3), `ffmpeg-kit-react-native` (§4.3, проект
архивирован апстримом — нужен форк или нативный композитинг) и `react-native-sensors` (§6.11 C).
Занесено в Фазу 0 как отдельная проверка.

## ADR-004 — Web-таргет удалён

**Статус:** принято
**Контекст:** при первичной настройке проекта в репозиторий были добавлены `react-dom` и
`react-native-web`, потому что шаблон Expo объявляет web в `app.json` и в скриптах.
**Решение:** web-зависимости и web-таргет удалены; `platforms` ограничен `["ios", "android"]`.
**Обоснование:** SPEC §2.2 прямо относит web-версию к тому, что **не входит в MVP**. Ядро продукта —
будильник (§4.1) и запись видео (§4.3) — в браузере нереализуемо в принципе.
**Последствия:** `npm run web` больше нет. Если web понадобится как лендинг под инвайт-ссылки
(§7.7, `rise.app/j/{code}`) — это отдельный проект, а не таргет мобильного приложения.

## ADR-005 — Монорепозиторий на npm workspaces

**Статус:** принято
**Контекст:** SPEC §3.2 задаёт структуру с `apps/mobile`, `packages/shared`, `supabase/`.
**Решение:** npm workspaces (`apps/*`, `packages/*`), единый lock-файл в корне.
**Обоснование:** структура задана SPEC; npm workspaces — минимальный инструмент, который её
поддерживает, без добавления Nx/Turborepo. Соответствует правилу «выбирай самое простое решение».
**Последствия:** Metro должен резолвить символические ссылки из корневого `node_modules`.
Проверено: импорт `@rise/shared` из `apps/mobile` бандлится без дополнительной настройки
`metro.config.js` (Expo SDK 57). При добавлении второго пакета в `packages/*` проверить повторно.

## ADR-006 — `packages/shared` содержит только типы, без значений денежных долей

**Статус:** принято
**Контекст:** SPEC §8.2 требует хранить доли распределения (`settings.stake_split`) на сервере и
**не хардкодить в клиенте**. SPEC §3.3 — вся денежная логика только на сервере.
**Решение:** в `packages/shared` лежат типы доменных сущностей и только те константы, которые
являются правилами продукта, а не денежной политикой: окно испытания (5 мин), курс деревьев,
множитель RISE+.
**Обоснование:** доли 50/30/20 и сервисный сбор $0.30 — предмет изменения без релиза приложения;
попадание их в бандл клиента означает рассинхрон при первом же изменении конфига.
**Последствия:** экран выбора ставки (§6.6) обязан получать разбивку с сервера и не считать её сам.
Это влияет на дизайн API — нужен эндпоинт, отдающий текущий `stake_split`, до реализации Фазы 5.

## ADR-007 — Фаза 0 не может быть закрыта в текущем окружении

**Статус:** требует подтверждения
**Контекст:** SPEC §17 запрещает начинать Фазу 1, пока не закрыта Фаза 0, а DoD Фазы 0 (§4.1) —
20/20 срабатываний будильника на пяти физических устройствах (2 iPhone + 3 Android, обязательно
Xiaomi/Huawei) при закрытом приложении и включённом энергосбережении.
**Решение:** UI и Фаза 1 не начинаются. В репозитории — только каркас, документы и контракт типов.
**Обоснование:** физических устройств нет; ни симулятор, ни CI не воспроизводят агрессивный киллинг
фоновых процессов MIUI/EMUI, ради которого этот DoD и написан. Заявить Фазу 0 закрытой по
результатам симулятора — значит обойти главную проверку продукта.
**Последствия:** ближайшие шаги, не требующие устройств, перечислены в [BACKLOG.md](./BACKLOG.md),
раздел «Готово к работе». Спайк 2b (заявка в Apple на Critical Alerts entitlement) — **человеческое
действие, не кодовое**, и по SPEC §17 подаётся в первую неделю: рассмотрение занимает недели и
является критическим путём.
